## Version Safety: Controlled SAP LUW and Outbound Calls

| Feature | Introduced | Practical impact if unavailable |
|---|---|---|
| `CL_ABAP_TX` (`modify( )`/`save( )` static methods — explicit Controlled-SAP-LUW transactional-phase control) | Release 792 (2305 / 2023 Q2) | Cannot explicitly force a phase switch outside of RAP's implicit management; on an older target, an outbound call that needs to run specifically in the save phase can only get there by being wired into a RAP save-sequence method (determination `on save`, or the saver class) — there's no standalone way to declare "I am now in the save phase" in plain ABAP code |

**Why this matters for the outbound-HTTP pattern**: the canonical `cl_http_destination_provider`/`cl_web_http_client_manager` pattern in this skill's SKILL.md body has no release gate of its own (also verified zero-hit against the release news) — but *where in a RAP transaction you're allowed to call it* is governed by the Controlled SAP LUW's transactional contracts, which is a real, verified constraint:

- `COMMIT ENTITIES` implicitly triggers `COMMIT WORK` (or `COMMIT WORK AND WAIT` if the local update fails) — meaning a RAP save is always a **local or synchronous** update, **never** an asynchronous one. Don't design an outbound-HTTP-in-a-RAP-save pattern assuming the classic bgRFC-style "fire and forget, handled later by an update task" model — that bundling technique is not available in ABAP Cloud's restricted language version at all (confirmed: `17_SAP_LUW.md`'s own "SAP LUW in ABAP Cloud and RAP" section states the bundling techniques listed elsewhere in that cheat sheet aren't available in ABAP Cloud, and that local update is the default there).
- Some APIs are **classified** with a transactional-phase restriction (`IF_ABAP_TX_SAVE`, etc.) that a controlled-SAP-LUW-aware runtime enforces — calling a *save*-phase-classified API during the *modify* phase (RAP interaction phase or early save phase) raises a runtime error. The verified example in the source cheat sheet is `CL_BCS_MAIL_MESSAGE`'s `send_async` method (classified `IF_ABAP_TX_SAVE`) — calling it from a RAP handler method (which runs in the *modify* phase by default) is a violation. **No equivalent classification claim is made for the HTTP-client classes** — don't assume `cl_web_http_client_manager`/`execute( )` is unclassified just because it wasn't flagged; check the class's own transactional-contract info in ADT (F2 on the method) before relying on calling it from an interaction-phase determination in a design that matters.

## Decision Guidance: Where in the RAP Transaction Should the Outbound Call Live?

The SKILL.md body's code sample shows the mechanics but not the placement decision. Use this framework:

- **Read-only outbound call whose result the UI should reflect before save** (e.g., a live credit-check API call triggered by a field change): call it from a `determination ... on modify` — this runs in the interaction/early-save (*modify*) phase, which is fine for a call with no side effect on the external system.
- **Outbound call that writes/commits something on the external system as a side effect of this transaction succeeding** (e.g., posting a document to a partner system once the local save is guaranteed): this needs to happen in the *save* phase — either a determination `on save`, or (per [Skill: rap]'s own deep-dive) a managed BO `with additional save`, or the saver class's `save_modified`. Calling an external-system-mutating request from the *modify* phase risks the external write happening even if the local RAP transaction subsequently fails/rolls back — there is no distributed transaction here, only the local SAP LUW.
- **A call that's slow, unreliable, or must not block the user's save at all**: given that classic asynchronous bundling isn't available in ABAP Cloud, don't try to force async behavior into the RAP save sequence itself. Decouple instead — either emit a RAP business event ([Skill: rap-business-events]) that a separate consumer picks up after the commit, or schedule an **Application Job** (already listed as a "Useful Fiori App" in `references/btp-setup-walkthroughs.md`) to perform the outbound call outside the user's transaction entirely.

## Decision Guidance: One Communication Scenario per External System, or Shared?

The SKILL.md body's concept table already establishes the mental model (scenario = design-time template, system/arrangement = runtime config) — the practical sizing question it doesn't answer:

- **Default to one Communication Scenario per logical integration purpose** (e.g., "send outbound sales confirmations," not "talk to SAP CPI" or "talk to Vendor X") — the scenario is a transportable ADT object defining which inbound/outbound services and auth methods are exposed, so scope it to *what* is being integrated, not *who* the current partner happens to be.
- **Use multiple Communication Systems + Arrangements against the same scenario** when the same integration purpose needs to reach different endpoints — e.g., DEV/QA/PROD instances of the same partner system, or several partner systems that all consume the identical outbound payload shape. This is exactly what the scenario/system split is *for*: swap the runtime target without touching the transported scenario definition or the ABAP code that resolves it via `create_by_comm_arrangement`.
- **Only create a second scenario for the same purpose** when the partner systems genuinely need different auth methods, different service sets, or different lifecycle (e.g., one partner needs OAuth 2.0 and another only supports Basic, and the scenario's "Allowed Auth Methods" list would otherwise have to stay permissive for both when only one should ever be used against a given system) — otherwise a single scenario with per-arrangement auth selection is simpler to maintain and audit.
